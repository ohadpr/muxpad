# CEO pane — orchestration plumbing + a pinned singleton agent

**Date:** 2026-08-21
**Status:** Part A SHIPPED. Part B was built, then RETIRED (`65f17b9`). Kept as
the design record for the plumbing, not as a description of the app.

- **Part A (§A1–A6) — shipped and load-bearing.** `muxpad pane read/send`,
  `pane list --all`, `muxpad agent transcript/send/wait`, `muxpad watch` and
  `GET /api/events` are all live, and the universal agent-instructions seed
  (`server/src/agent-instructions.ts`) teaches every backend to use them. This
  is the whole orchestration surface muxpad has.
- **Part B (§B*) — gone.** The singleton pane, its crown row, `/api/ceo`,
  `server/src/ceo.ts` and the playbook seeding were all deleted. The
  orchestrator turned out to be nothing but a pinned chat the user owns: the
  living sidebar's pinned block does what the hardwired slot did, and ⚡ Do mode
  (`server/src/agent-modes.ts`) carries the behavioural contract the playbook
  used to. Installs that already had the hidden container get a one-shot,
  non-destructive release — `server/src/resident-release.ts`.
- Read Part B below as history. Nothing in it describes current code.

**Original goal:** one always-present agent pane, pinned at the top of the sidebar, that
looks and feels like a regular agent chat but can introspect, drive, and wait on
every other pane — a central place to get work done.

Two halves, deliberately separated:

- **Part A — plumbing**: generic CLI/HTTP primitives any agent (or script) can
  use: read a terminal pane's scrollback, send it keystrokes, enumerate
  everything flatly, subscribe to events, block until an agent finishes a turn.
  These are muxpad capabilities, useful beyond the CEO.
- **Part B — the CEO primitive**: a server-owned singleton agent pane, pinned in
  the sidebar, whose *powers* come entirely from Part A + a playbook CLAUDE.md.
  No orchestration policy is baked into muxpad code — policy stays in
  prompt-space where it can be iterated without a deploy.

Everything below lives in the **main server** (`server/src/…`) and the CLI
(`scripts/muxpad`). ptyd is untouched in v1 — see §A1 for how scrollback reads
avoid a ptyd change. Deploying this is a main-server restart only; terminals
and the ptyd socket survive.

## Part A — missing plumbing

### A1. Read a terminal pane's scrollback

**The gap.** The 2MB `RingBuffer` lives in ptyd and is only delivered as a
binary replay burst when a client attaches WS `/ws/pane/:id` (proxied by
`ptyd-client/proxyAttach.ts` to ptyd's `/pty/:id`). No HTTP GET, no CLI verb.
A supervisor cannot "look at" a terminal pane.

**v1 — no ptyd change.** The main server implements
`GET /api/panes/:id/scrollback` by acting as a pty client itself:

1. Open a WS to ptyd `/pty/:id` (same path `proxyAttach` uses).
2. Collect the replay burst (`OP_OUTPUT` frames). The burst is bounded by the
   ring size; treat a short quiet gap (~150ms) after the last frame, or an
   explicit end-of-replay marker if the protocol has one, as "replay complete."
3. Close the WS. Decode, ANSI-strip (keep a `?raw=1` escape hatch), optionally
   trim to the last `?lines=N` lines, return `text/plain`.

Caveats to verify during implementation:
- Attaching must not perturb seen/unread semantics — `markSeen` is an explicit
  RPC so this should hold, but confirm no attach-side effects (resize, seen,
  client-count-driven behavior) fire on a headless attach.
- Concurrent attach from the real browser client must be unaffected (ptyd
  already supports multiple pty clients; `closePtyClients` exists for the
  forced-detach case, don't call it).

**v2 (later, opportunistic).** A proper `snapshot` control RPC in ptyd
(`PaneRuntime.snapshot()` already exists at `runtime/PaneRuntime.ts:423`; it's
just not exposed over `/control`). Cleaner and cheaper than a fake attach, but
it requires a ptyd redeploy, which kills every terminal. Ship it with the next
ptyd bounce that's happening anyway; never bounce ptyd just for this.

**CLI.**

```
muxpad pane read [<id>] [--lines=N] [--raw]
```

`<id>` defaults to `MUXPAD_PANE_ID` (mostly useless for self, but consistent).
Output is plain stripped text on stdout — grep-able.

### A2. Send input to a terminal pane

**The gap.** `OP_INPUT` (0x01) frames over `/ws/pane/:id` are the only input
path; the mobile composer is the only consumer.

**Design.** `POST /api/panes/:id/input` — the main server opens the same pty
WS, writes the input frame(s), closes. Body:

```json
{ "text": "make test", "enter": true }
```

or, for control sequences:

```json
{ "keys": ["ctrl-c"] }
```

Named keys (small fixed table, translated server-side): `enter`, `esc`,
`tab`, `up`, `down`, `left`, `right`, `ctrl-a` … `ctrl-z`. `text` and `keys`
are mutually exclusive; `enter: true` is sugar for appending `\r`.

**CLI.**

```
muxpad pane send <id> "text" [--no-enter]
muxpad pane send <id> --key=ctrl-c
```

`--no-enter` inverts the default because the dominant use is "run this
command." Refuse (400) if the pane has no live pty (`isRunning: false`) rather
than silently buffering.

**Safety.** This is typing into someone's live terminal. No confirmation
prompt (it's a personal tool, the API is already unauthenticated), but the
server logs every input injection with source + pane id so a misbehaving
orchestrator is auditable.

### A3. Flat pane enumeration

**The gap.** `pane list` is tab-scoped; `GET /api/tabs?workspaceId=` is
workspace-scoped. A supervisor must fan out over workspaces → tabs → panes.

**Design.** `GET /api/panes` — every pane across all workspaces, decorated
(same `decoratePane` path: `title`, `foreground_cmd`, `attention`, `busy`,
`unread`, `app_urls`, `cwd`, `face`, `startup_cmd`, `isRunning`), each row
joined with `{tab_id, tab_name, workspace_id, workspace_name}`.

**CLI.**

```
muxpad pane list --all [--json]
```

Human output: one line per pane —
`<pane-id>  <ws>/<tab>  <face>  <busy|idle>  <title|foreground_cmd>`.
This is the CEO's "org chart" view.

### A4. Agent turn lifecycle on the global bus

**The gap.** `turn-start` / `turn-done` are broadcast only to that pane's
`/ws/chat/:paneId` subscribers. The global bus (`events.ts` → `/ws/events`)
only sees a thin `agent_session.updated`. A supervisor watching N workers must
hold N chat sockets open.

**Design.** In `ws.ts`, where the runner's `turn-start` / `turn-done` messages
are handled, additionally emit on the `EventBus`:

```ts
{ type: 'agent_turn', paneId, phase: 'start' | 'done', sid, backend }
```

Extend the `MuxpadEvent` union (`shared/src/types.ts:219`); it fans out to
`/ws/events` for free. Include `phase: 'fatal'` when the runner reports
`fatal`, so a supervisor learns about dead workers, not just finished ones.

No payload beyond ids — a subscriber that wants content pulls the transcript
(A6). Keeps the bus thin.

### A5. Script-friendly subscription: SSE + `watch` + `wait`

**The gap.** `/ws/events` requires a WS client; a bash-driven (or
Bash-tool-driven) supervisor can't `curl` it.

**Design.**

- `GET /api/events` — SSE mirror of `/ws/events`. One `data:` line per
  `MuxpadEvent`, JSON. Optional `?types=agent_turn,pane.updated` filter.
- CLI:

```
muxpad watch [--types=a,b] [--json]        # stream events, one JSON line each
muxpad agent wait <paneId> [--timeout=SEC] # block until that pane's turn-done
```

`agent wait` is the orchestration workhorse: subscribe to SSE filtered to
`agent_turn`, resolve on `done`/`fatal` for the pane (exit 0 / exit 2), honor
`--timeout` (exit 3). If the pane is already idle when called, return
immediately (check `busy` via A3 first — avoids the missed-event race by
checking state *after* subscribing). This gives the CEO tokenless waiting: run
`muxpad agent wait` via Bash in the background and get re-invoked when the
worker finishes.

### A6. Agent CLI verbs (wrappers over existing HTTP)

All of these endpoints exist; none have CLI verbs, which means an agent needs
hand-rolled `curl` + jq. Add:

```
muxpad agent list [--json]                  # GET /api/agent-sessions — all sessions
muxpad agent send <paneId> "message"        # POST /api/agent-sessions/:paneId/send
muxpad agent transcript <paneId> [--tail=N] # last N normalized transcript entries
muxpad pane summarize <id>                  # POST /api/panes/:id/summarize
```

`agent transcript` needs one small server addition:
`GET /api/agent-sessions/:paneId/transcript?tail=N`, implemented on the server
with the existing `TranscriptReader` / `normalizeTranscriptLine` machinery
(covers both Claude's `~/.claude/projects/**/<sid>.jsonl` and the
`~/.muxpad/agent-transcripts/` backends). Output: normalized JSONL — role,
text, tool-use summaries. Don't make CLI consumers parse raw backend formats.

`agent send`'s 202/409 semantics surface as exit codes: 0 sent, 0 queued
(with a `queued` note on stderr), 1 rejected (print the reason).

### A7. Explicit non-goals (for now)

- **Browser-pane driving.** iframe panes stay opaque — no DOM bridge,
  no postMessage protocol. The CEO can set a pane's URL and that's it.
- **Output-pattern triggers** ("wake me when this pane prints ERROR").
  `pty-scanner.ts` / `app-url-detector.ts` is the template; defer until a real
  need shows up — `pane read` + polling covers the near term.
- **Parent/child agent structure & report channels.** `agent new` + `agent
  wait` + `summarize` compose into delegate→await→collect without new schema.
  If a real hierarchy need emerges, design it then.
- **Auth.** Everything stays unauthenticated; the CEO gets root over the
  mosaic for free, same as any in-pane process today.

## Part B — the CEO primitive

### B1. What it is

A **server-owned singleton agent pane**: exactly one, exists on every device,
survives restarts, cannot be deleted, pinned above the workspace tree in the
sidebar. It renders with the standard `ChatPane` — it *is* a regular agent
pane (`face: 'chat'`, `startup_cmd: 'muxpad agent'`, runner-owned, durable
send queue, all existing machinery). What makes it the CEO is placement,
persistence, and its playbook — not a special code path in the runner.

### B2. Storage: migration 19

`panes.tab_id` is NOT NULL, so the pane needs a backing tab; tabs need a
workspace. Rather than nullable FKs (SQLite table rebuild) use a hidden system
container + a pointer:

```sql
-- migration 19 (18 is agent_queue; 2–5 are burned, see migrations.ts:67)
CREATE TABLE globals (
  key   TEXT PRIMARY KEY,
  value TEXT NOT NULL
);
ALTER TABLE workspaces ADD COLUMN hidden INTEGER NOT NULL DEFAULT 0;
```

- One hidden workspace (`name: '· system ·'`, `hidden: 1`) holding one tab
  (`name: 'ceo'`) holding the CEO pane. `hidden` workspaces are excluded from
  `GET /api/workspaces` (and thus the sidebar tree) unless `?all=1`.
- `globals` rows: `ceo_pane_id`, `ceo_tab_id`. Server-side pointer — the doc
  surface's localStorage-pointer trick (`doc-store.ts:71`) is per-device and
  wrong here; the CEO must be the same pane from every browser.
- Deletion guards: `DELETE /api/panes/:id`, `DELETE /api/tabs/:id`,
  `DELETE /api/workspaces/:id` return 409 when the target is (or contains) the
  CEO pane. Respawn stays allowed.

### B3. Ensure-on-boot

`ensureCeoPane()` runs at server startup (next to the pane-reaper init):

1. If `globals.ceo_pane_id` resolves to a live pane row → done.
2. Else create hidden workspace/tab/pane inside one transaction, following
   `routes/tabs.ts:66-92` (`bootstrap: 'agent'`) exactly, with:
   - `cwd: ~/.muxpad/ceo/` (created if missing — see B5)
   - `env: { MUXPAD_ROLE: 'ceo' }` (panes already have an `env` column; the
     runner and playbook can detect the role)
   - `face: 'chat'`, `startup_cmd: 'muxpad agent'`
3. Write the `globals` pointers, emit the usual `pane.added`/`tab.added`
   events, then eagerly `ptyd.ensurePane(...)` so the CEO is alive with zero
   browsers open — same as `routes/tabs.ts:104`.

The existing dead-runner respawn sweep in `ws.ts` keeps it alive thereafter.
Also expose `GET /api/ceo` → `{pane_id, tab_id}` (ensures, then returns) so
the client and CLI never hard-code ids.

### B4. UI: pinned sidebar row + route

- **Sidebar.** New pinned block in `NavTree.tsx` between `<nav
  className="navtree">` (:304) and `.navtree-scroll` (:313) — the one slot
  above the scrolling tree. A single row: icon (✳ or 👑), label "CEO", and the
  same busy/unread/attention badges `TabRow` shows, driven by the decorated
  CEO pane from `pane.updated` events. Always visible in both sidebar and
  sheet variants; not drag-reorderable.
- **Route.** `/ceo` in `router.tsx`, following the `PopoutView` pattern
  (`/p/$paneId`, `router.tsx:52`): resolve the pane id via `GET /api/ceo`,
  render the single pane chromelessly. Keep the component mounted-but-hidden
  when navigating away (same trick `WorkspaceLayout` uses for `TabView`s) so
  chat state survives switching.
- The CEO row navigates to `/ceo`; the hidden system workspace never appears
  in the tree.

### B5. The playbook: `~/.muxpad/ceo/CLAUDE.md`

The CEO's capabilities are taught, not hard-coded. `ensureCeoPane()` seeds
`~/.muxpad/ceo/` with a CLAUDE.md (written once, never overwritten — the user
owns it after creation) documenting the orchestration surface:

- The org chart: `muxpad pane list --all`, `muxpad agent list`.
- Reading: `muxpad pane read <id>`, `muxpad agent transcript <paneId>`,
  `muxpad pane summarize <id>`.
- Directing: `muxpad agent send`, `muxpad agent new "task"`, `muxpad pane
  send`, pane/tab/workspace CRUD.
- Waiting: `muxpad agent wait <paneId>` (run in background via Bash),
  `muxpad watch`.
- House rules: don't inject input into a terminal a human is actively typing
  in (check `foreground_cmd`/recent activity first); prefer `agent send` over
  `pane send` for agent panes; summarize before pulling full transcripts.

Iterating on CEO behavior = editing this file. No deploy.

### B6. cwd and project context

`~/.muxpad/ceo/` deliberately has no project markers, so `agentCwd` leaves it
alone and the CEO starts with global context only (its CLAUDE.md + the user's
`~/.claude/CLAUDE.md`). When work is project-shaped, the CEO's move is to
*delegate*: `muxpad agent new --cwd=<project> "task"` — workers get project
context, the CEO keeps altitude. The playbook says exactly this.

## Phasing

1. **Phase 1 — read/write/enumerate** (server + CLI, no schema change):
   A1 scrollback (WS-attach v1), A2 input, A3 flat list, A6 agent verbs
   (including the transcript endpoint). Independently useful; testable from
   any pane immediately.
2. **Phase 2 — events**: A4 `agent_turn` on the bus, A5 SSE + `watch` +
   `agent wait`. Depends on nothing in Phase 1 but is what makes waiting
   tokenless.
3. **Phase 3 — CEO**: migration 19, `ensureCeoPane`, `GET /api/ceo`, deletion
   guards, sidebar pin, `/ceo` route, playbook seed.
4. **Later**: ptyd `snapshot` RPC (with the next planned ptyd bounce),
   output-pattern triggers, browser-pane bridge, parent/child reporting —
   each only when a concrete need appears.

## Rollout notes

- All three phases deploy with a **main-server restart only**; ptyd and every
  terminal survive. Do not bounce ptyd for any of this.
- The server restart still kills live agent-runner *turns* mid-flight (runners
  reconnect, queues drain, but in-progress background subagents/wakeups die) —
  deploy at a quiet moment of the user's choosing.
- Migration 19 is additive (new table + defaulted column); no data rewrite.

## Open questions

1. **Replay-complete detection** in A1's WS-attach: is there an explicit
   end-of-replay marker in the pty protocol, or do we rely on the quiet-gap
   heuristic? (Check `proxyAttach` / ptyd's attach path first.)
2. Should `muxpad agent wait` also accept `--any` (first of several panes to
   finish) for fan-out/join patterns? Cheap to add; deferrable.
3. CEO model/backend choice: hard-code claude, or read `--backend`/`--model`
   from a `globals` row so it's switchable without touching the pane? (Lean:
   plain `muxpad agent`, switch via the existing pane backend controls.)
4. Does the CEO tab want a distinct `view_mode`/chrome (e.g. hide the terminal
   face entirely), or is the standard chat/terminal face-flip fine? (Lean:
   standard — it's "a regular agent pane" by design.)
