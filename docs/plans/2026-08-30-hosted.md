# Hosted — apps as a first-class primitive, artifacts with versions

Status: **Built.**

## The problem

Notes and Reader are web apps. Each burned a permanent TAB — `muxpad serve --url …
-- ./start` in a shell pane (`01KXAYH4EX12XDXJHB736XEFWQ`,
`01KXQGRMDY8XEQNPH6T1ZBFBP3`) — purely to keep a process alive. Viewing one meant
navigating to that tab; closing the tab killed the app. They are not
conversations and had no business in the tab tree.

Separately, agents were spawning `acme-creative`, `acme-creative2` …
`acme-creative6` instead of updating one artifact, because `--name`
creates-or-replaces and nothing told them to look first.

## §1 Apps

### The one design decision

**An app is a supervised `muxpad serve` pane with no presence in the tab tree.**
It lives in a hidden workspace (`workspaces.hidden`, migration 19 — the same
mechanism the retired resident pane used, and the reason `visibleWorkspaces()`
already filters it out).

This is not a shortcut. Apps must survive a MAIN-SERVER restart, and the only
thing in muxpad that does is ptyd. A second process supervisor living in the main
server would die with it and take every app down on each deploy — precisely the
split ptyd exists to prevent. So there is **no new supervisor**. An app borrows
what a pane already has:

| need | who already does it |
|---|---|
| owns the process across a server restart | ptyd |
| restarts a crashing command, with backoff | `muxpad serve` (in-pane) |
| rebuilds the pty after a **ptyd** restart | `serve-supervisor.ts` (`muxpad serve%` sweep) |
| renders the app's logs | `/p/:paneId` → `XtermPane` |
| injects `MUXPAD_*` env, tracks cwd | `PaneRuntime` |

What is genuinely new is small: a hidden container, a row that outlives the
pane, and reconciliation between the two.

### The invariant

> a materialised pane exists **⟺** the app row is enabled

`stop()` disables the row **before** tearing the pane down (the reverse order is
a live restart loop against the supervisor); `remove()` tears down **before**
deleting the row (the reverse strands a pty that `disabledPaneIds()` would no
longer name, so the supervisor would adopt and keep it alive forever).

`autostart` acts at boot **by translation, not exception**: an enabled app with
`autostart = 0` is stopped at boot (enabled → 0) rather than left
enabled-but-paneless. That keeps the invariant total — there is no state where
the registry says "running" and no pane exists — and the user sees an honest
`stopped` with a Start button, which is what turning autostart off asked for.

### Status is MEASURED, never inferred

Two independent observations, folded by `deriveAppState`:

1. **process liveness** — `ptyd.hasPane`. A throw means ptyd is unreachable, so
   liveness is **unknown** (`pty: null`), never "dead". Same nuance the
   supervisor makes; without it a 2-minute ptyd outage would report every app as
   failed.
2. **reachability** — the server-side probe (`url-health.ts`). The only probe
   that can distinguish "proxy up, backend dead" (502/503/504 → `gateway`) from
   healthy. A browser provably cannot: its no-cors probe sees `status === 0`.
   Both real apps sit behind exactly such a proxy.

Precedence: `stopped` (the user's decision outranks every observation) >
`gave_up` (the supervisor's own ledger) > `starting` (no pty / not probed / in
the 20s startup grace) > `running` > `unreachable`.

The startup grace exists because every server has seconds between its pty
existing and its port listening; calling that `unreachable` would flash a
failure on every legitimate start, and users learn to ignore a light that lies.

### One status vocabulary

`APP_STATE_STATUS` maps all five app states onto the existing five-state pane
vocabulary, so the Hosted list draws marks with the same `StatusMark` and the
same colour rule as the sidebar. Many-to-one on purpose: the **mark** answers
"should I look?", the row's **text** answers "what exactly?". A sixth mark so
`running` and `stopped` could differ in the rail would have cost the property
that makes the rail scannable — that a mark means the same thing everywhere.

## §2 Artifacts

Republishing already staged atomically and moved the old tree aside; it just
deleted it. It now **rotates**: `<slug>` → `<slug>@2` → `@3`, oldest falling off
at `PUBLISH_VERSIONS_KEEP` (3). Each version is a real directory under the public
root, so `/slug@2/` is served by the existing static app — no new routing, no new
trust surface.

Sibling dirs, not `<slug>/@2/` nested inside the current tree: nesting would put
history inside the thing being replaced (each publish would have to lift it out
and put it back, losing atomicity), fold old versions into the current one's byte
count, and collide with a source containing an `@2` entry. `@` is not in
`SLUG_RE`, so `<slug>@<n>` can never collide with a real slug and the listing
filter already excludes it.

Numbering is **relative age** (`@2` = previous), not monotonic. The question
people ask is "what did this look like before I broke it", and that is a fixed
URL under relative numbering. The cost — `@2` means different bytes after the
next publish — is acceptable for a rollback aid, and the UI lists versions with
dates.

`--update <slug>` refuses to **create**. `--name` creates-or-replaces, so a typo
silently mints a new artifact; `--update` turns the same typo into a readable
404. The agent-instructions seed now tells agents to run `publish --list` first
and reuse a slug when updating the same thing.

DELETE removes the versions too — leaving `@2` serving after a delete the user
believed took the artifact off the internet is the one surprise a public surface
must never spring.

## §3 No public gallery

The public root keeps 404ing (`public-server.ts`). Enumerable artifacts are a
leak: knowing the hostname must reveal nothing. The gallery lives inside the
muxpad UI, which is tailnet-only. Asserted in `publish-versions.test.ts` and
again over real HTTP in `integration/hosted-e2e.test.ts`.

## §4 The Hosted view

`/hosted` — a child of the app layout, not of a workspace. That placement is the
feature: `AppLayout` renders its `<Outlet/>` whenever the URL carries no
workspace, so Hosted inherits the brand/settings chrome while occupying no tab.

`/hosted/a/:slug` is the app viewer: a **route**, not a tab. Leaving it issues no
request at all, so closing the view provably cannot stop the app.
`?logs=true` swaps the iframe for the app's own pane terminal.

The view **polls** (3s, paused while the page is hidden). An app's state is
measured, so the interesting transitions — a server dying, a proxy starting to
502 — happen with nothing touching the database and no mutation to emit an event
on. Polling also keeps the hidden container off the event bus entirely, which is
what guarantees it cannot leak into the sidebar.

Mobile-first: the base CSS **is** the phone layout (rows stack, actions wrap,
44px controls); the 720px query is the desktop enhancement. Nothing is
hover-revealed, so the installed PWA is the same view, not a degraded one.

## §5 Migration

`apps/adopt-serve-panes.ts`, one-shot behind `serve_panes_adopted`. The gentlest
change that works: **the pane is not touched at all** — same id, same pty, same
running server — only its tab's parent workspace changes, from the user's visible
one to the hidden container. The app never goes down, so adoption is safe on a
live machine. Nothing is deleted, including the workspace the tabs came out of.
Anything ambiguous (a serve pane sharing a tab, an unparseable command) is
skipped with a logged reason.

Verified against a consistent `.backup` of the live DB (v21 → v23): both apps
adopted with the right url/cwd/command, container hidden, 19 panes and 19 tabs
before and after, second run a no-op.

## Deliberately omitted

**A per-app "make public" toggle.** Requirement 11 allowed it or an explicit
omission. Omitted: more risk than value. Notes and Reader hold personal data;
the value of the toggle is one funnel command the user can run by hand, while
its cost is a UI affordance one mis-tap from putting a personal notes app on the
open internet, plus a second code path near the funnel — the one place in muxpad
where a bug is irreversible and public. The asymmetry is not close. `publish`
remains the only way muxpad exposes anything, and it exposes bytes the user
chose, never a live app's port.

**Events for app changes.** The Hosted view polls instead. See §4.

**A "+ Add app" form.** Registering an app needs a command and a directory; the
empty state teaches the one-liner instead, which is also what an agent would use.
